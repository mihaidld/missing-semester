2. Take a look at the various ways to specify version requirements for dependencies in Rust’s build system. Most package repositories support similar syntax. For each one (caret, tilde, wildcard, comparison, and multiple), try to come up with a use-case in which that particular kind of requirement makes sense.

Default requirements specify a minimum version with the ability to update to SemVer compatible versions. Versions are considered compatible if their left-most non-zero major/minor/patch component is the same.

Caret requirements are the default version requirement strategy. This version strategy allows SemVer compatible updates. They are specified as version requirements with a leading caret (^).
^1.2.3 is an example of a caret requirement. It allows updates that can fix bugs (increase patch version to 1.2.1) or even add features still being backwards compatible (increase minor version to 1.3.0)

Tilde requirements specify a minimal version with some ability to update. If you specify a major, minor, and patch version or only a major and minor version, only patch-level changes are allowed. If you only specify a major version, then minor- and patch-level changes are allowed.
~1.2.3 is an example of a tilde requirement. It restricts updates only patches are allowed (1.2.4). You might want this to avoid accepting updates that change the API (after minor update).

Wildcard requirements allow for any version where the wildcard is positioned.
1.* is an example of wildcard requirements. This allows any version with major 1 because it requires the API from 1.0.0, doesn't necessary require any specific later minor update any version with major 1 because it requires the API from 1.0.0, doesn't necessary require any specific later minor update

Comparison requirements allow manually specifying a version range or an exact version to depend on.
Here are some examples of comparison requirements:
>= 1.2.0, > 1, < 2, = 1.2.3. An exact version misses possible patches an restricts too much, but might be useful in case we want to block to current code, a lower cap might bring incompatibility after major update while upper cap misses minor or patch updates. 

Multiple version requirements can be separated with a comma, e.g., >= 1.2, < 1.5. This restricts to only specific range to avoid too many compatibilities.

3. Git can act as a simple CI system all by itself. In .git/hooks inside any git repository, you will find (currently inactive) files that are run as scripts when a particular action happens. Write a pre-commit hook that runs make paper.pdf and refuses the commit if the make command fails. This should prevent any commit from having an unbuildable version of the paper.
Rename pre-commit.sample script tp pre-commit and add at the top
# Check the exit status
if make paper.pdf
then
# Command succeeded
        echo "Buildable version of paper available"
        make clean
        exit 0
else
# Command failed
        echo "Command failed: make paper returned a non-zero exit status"
        exit 1
fi

Created repo as per GitHub pages instructions then added inside a yaml config file for GitHub Actions
/.github/workflows/github-actions-shellcheck.yml
name: GitHub Actions Shellcheck scripts
run-name: ${{ github.actor }} is checking out scripts via Shellcheck and GitHub Actions 🚀
on:
  push:
    branches:
      - main
permissions: {}
jobs:
  shellcheck:
    name: Shellcheck
    runs-on: ubuntu-latest
    steps:
      - run: echo "🎉 The job was automatically triggered by a ${{ github.event_name }} event."
      - run: echo "🐧 This job is now running on a ${{ runner.os }} server hosted by GitHub!"
      - run: echo "🔎 The name of your branch is ${{ github.ref }} and your repository is ${{ github.repository }}."
      - name: Check out repository code
        uses: actions/checkout@v5
      - name: Run ShellCheck
        uses: ludeeus/action-shellcheck@2.0.0
        with:
            # skip scripts wip/*
            ignore_paths: >-
              wip
            # fail only if there are errors in scripts but ignore styling, info and warnings.
            severity: error
      - run: echo "🍏 This job's status is ${{ job.status }}."
