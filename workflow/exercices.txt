2. Say you don’t want to start a process until another completes. How would you go about it? 
In this exercise, our limiting process will always be sleep 60 &. One way to achieve this is to use the wait command. 
Try launching the sleep command and having an ls wait until the background process finishes.

Run sleep for 60 sec in the background, wait for job id nb 1 (sleep 60), then ls
sleep 60 &; wait %1; ls   

However, this strategy will fail if we start in a different bash session, since wait only works for child processes. 
One feature we did not discuss in the notes is that the kill command’s exit status will be zero on success and nonzero otherwise. kill -0 does not send a signal but will give a nonzero exit status if the process does not exist. 
Write a bash function called pidwait that takes a pid and waits until the given process completes. 
You should use sleep to avoid wasting CPU unnecessarily.

pidwait(){
    keep=1 #to control loop
    while [ $keep -ne 0 ]
    do
        #get non zero exit status if pid doesn't exist
        #redirect STDOUT and STDERR from kill to /dev/null
        if ! kill -0 "$1" > /dev/null 2> /dev/null; then
            keep=0 #kill received nonzero exit code so pid stopped
        fi
        sleep 1 #sleep 1s before next iteration try to avoid wasting CPU
    done
}
source pidwait.sh 
# call pidwait function sourced into shell session with argument pid of last command ($!)
# when pidwait exits loop ls is executed

# same shell session
sleep 30 &; pidwait $!; ls  
# different shell session

#1st session
sleep 30 &
[1] 32806    

#2nd session
pidwait 32806; ls

Remote Machines
Install a Linux virtual machine (or use an already existing one) for this exercise. If you are not familiar with virtual machines check out this tutorial for installing one.

Installed guest system Ubuntu 24.04, machine called "Ubuntu Server 24.04" on MacOs host system with Virtual Box. 
To start machine in headless mode (without display)
VBoxManage startvm "Ubuntu Server 24.04" --type headless
To stop it
VBoxManage controlvm "Ubuntu Server 24.04" poweroff

Go to ~/.ssh/ and check if you have a pair of SSH keys there. If not, generate them with ssh-keygen -o -a 100 -t ed25519. 
It is recommended that you use a password and use ssh-agent , more info here.
Edit .ssh/config to have an entry as follows

 Host vm
     User username_goes_here
     HostName ip_goes_here
     IdentityFile ~/.ssh/id_ed25519
     LocalForward 9999 localhost:8888

Use ssh-copy-id vm to copy your ssh key to the server.
sh-copy-id tries to authenticate via Public/Private keys, but in the beginning of the server
there is only user/password authentication so need to add optionPubKeyAuthentication to no
sh-copy-id -o PubKeyAuthentication=no myserver

Start a webserver in your VM by executing python -m http.server 8888. 
Worked with python3 -m http.server 8888

Access the VM webserver by navigating to http://localhost:9999 in your machine.
Edit your SSH server config by doing sudo vim /etc/ssh/sshd_config and disable password authentication by editing the value of PasswordAuthentication. Disable root login by editing the value of PermitRootLogin. Restart the ssh service with sudo service sshd restart. Try sshing in again.
PasswordAuthentication no

(Challenge) Look into what the -N and -f flags do in ssh and figure out a command to achieve background port forwarding.
ssh -f Requests ssh to go to background just before command execution, doesn't take over the prompt on host terminal. 
This is useful if ssh is going to ask for passwords or passphrases, but the user wants it in the background.
ssh -N Do not execute a remote command.  This is useful for just forwarding ports.  
Refer to the description of SessionType in ssh_config(5) for details.
ssh -L [bind_address:]port:host:hostport specifies that connections to the given TCP port or Unix socket 
on the local (client) host are to be forwarded to the given host and port, or Unix socket, on the remote side. 

ssh -Nf -L localhost:9998:localhost:8889 myserver
ssh -Nf -L 9998:localhost:8889 myserver
All requests to host's localhost port 9998 are forwarded to VM's port 8889 where a Python web server is running using
python3 -m http.server 8889
In essence, this connection creates a tunnel between host and guest, will run forever on the background. (Well, it can be killed albeit cumbersome.)
Check processes listening on port 9998
lsof -i tcp:9998
Kill processes to remove tunnel
pkill -af ssh
